## Architectural Findings: Registration in `src/index.ts` & `FORM_REGISTRY`

### The Current Registration Flow
When adding a new form today, **6 places** are touched:
1. `src/config/form-uuids.ts`: Form UUID and Name constant exports.
2. `src/config/form-registry.ts`: `FORM_REGISTRY` entry (`key`, `uuid`, `name`, `path`, `titleKey`, `title`, `slot`, `icon`, `order`).
3. `src/index.ts`: `FORM_MODULES` dictionary entry mapping key to dynamic import.
4. `src/index.ts`: Named exports destructuring (`aiims<Pascal>DashboardLink`, `aiims<Pascal>Dashboard`).
5. `src/index.ts`: Feature barrel export (`export * from './<key>'`).
6. `translations/en.json`: Key definitions.
*(Note: `src/routes.json` is already 100% automated via `scripts/generate-routes.ts` in the `prebuild` hook!)*

### Can `FORM_MODULES` and Named Exports be Derived from `FORM_REGISTRY`?
**Investigation Result:**
- **Why named exports exist:** OpenMRS Single-SPA extensions resolve named exports from `@aiims/esm-demographics-app` at runtime based on `routes.json` component strings (e.g. `module["aiimsAdjuvantDrugDashboardLink"]`). Because JavaScript/TypeScript specifications **disallow dynamic named exports** at runtime (`export const [name] = ...` is invalid syntax), named exports must be statically declared at bundle time.
- **How they can be derived:**  
  Just like `src/routes.json` is generated by `scripts/generate-routes.ts`, we can generate a single file: `src/generated-form-extensions.ts` (or expand `generate-routes.ts` to output both):
  - It reads `FORM_REGISTRY`.
  - It generates the static dynamic import map `FORM_MODULES`.
  - It generates the static named exports:
    ```typescript
    export const aiimsDemographicsDashboardLink = ...;
    export const aiimsDemographicsDashboard = ...;
    ```
  - It generates the barrel re-exports: `export * from './demographics'`.
  - `src/index.ts` simply does:
    ```typescript
    export * from './generated-form-extensions';
    ```
- **Trade-off Evaluation:**
  - **Option A (Derived via code generation script)**: Zero edits to `src/index.ts`. A new form only touches `form-uuids.ts`, `form-registry.ts`, the new folder, and `en.json`. `scripts/generate-routes.ts` generates both `routes.json` and `src/generated-form-extensions.ts` during `prebuild`.
  - **Option B (Explicit Marker Comments in `src/index.ts`)**: Keep `src/index.ts` manual and place marker comments (`// @create-form:modules-end`, `// @create-form:exports-end`, `// @create-form:barrels-end`).
  - **Recommendation**: Before implementing the scaffolder, execute **Option A** as a fast preparatory refactor. It eliminates 3 of the 6 touch points permanently and guarantees that `index.ts` never drifts from `FORM_REGISTRY`.

## Detailed Phase Specifications

### Phase 3: Thin 1-Click Deploy Pipeline (`npm run deploy:local`)

**Goal:** Wrap the proven `scripts/deploy_demographics.py` with pre-flight checks and validation without rewriting the core deployment logic.

#### Implementation Design
- **Script**: `scripts/deploy_pipeline.py` (or powershell/node runner `aiims-esm-demographics-app/scripts/deploy-local.ts`).
- **Steps**:
  1. **Docker Pre-flight**: Run `docker ps` and verify containers `frontend`, `backend`, `gateway`, and `db` are running and healthy. If stopped, fail immediately:
     `"Error: Docker environment not running. Run .\openmrs.ps1 start"`.
  2. **Type Check**: Execute `npm run typescript` in `aiims-esm-demographics-app` (must exit code 0).
  3. **Unit Tests**: Execute `npm run test` in `aiims-esm-demographics-app` (must exit code 0).
  4. **Production Build**: Execute `npm run build` in `aiims-esm-demographics-app` (triggers `generate-routes` + Rspack).
  5. **Deploy**: Invoke `python scripts/deploy_demographics.py` (which handles version bumping, container tar extraction, importmap update, and nginx reload).
  6. **Probe Verification**: Send HTTP request to `http://localhost/openmrs/spa/importmap.json`. Confirm HTTP 200.
- **Acceptance Check**:
  - Run `npm run deploy:local` (or `python scripts/deploy_pipeline.py`).
  - Verify all 6 steps pass with clear terminal output.
  - Verify HTTP 200 probe succeeds.
  - Verify git working tree is clean.

### Phase 1: Form Scaffolder CLI (`npm run create-form`)

**Goal:** Generate complete starter files, registration entries, and translations for a new form with strict rollback safety.

#### Spec Fixes & Rules
1. **CLI Arguments**: Use `--icon` flag only.
   - Usage: `npm run create-form -- <key> "<Form Name>" [--icon=IconName] [--concepts=c1,c2] [--keep-on-fail]`
   - Example: `npm run create-form -- blood-gas-analysis "AIIMS Visit: Blood Gas Analysis" --icon=Activity`
2. **Imports in Templates**:
   - Templates must import directly from `../config/form-uuids` and `../config/concepts` (not the `../constants` shim).
3. **Dynamic Order Computation**:
   - Read existing entries in `src/config/form-registry.ts`.
   - Compute `order: Math.max(...FORM_REGISTRY.map(e => e.order || 0), 0) + 1` (or next sequential index).
4. **AST / Marker Updates**:
   - Use explicit, unambiguous marker comments in `src/config/form-uuids.ts`:
     `// @create-form:uuids-end`
   - And in `src/config/form-registry.ts`:
     `// @create-form:registry-end`
5. **Complete Translations**:
   - Add all 8 standard keys required by `FormDashboardShell`, `EmptyState`, toolbar, and card:
     - `aiims<Pascal>Title`: `"<Form Name>"`
     - `<camel>Details`: `"<Form Name> Details"`
     - `loading<Pascal>`: `"Loading <Form Name>..."`
     - `noRecorded<Pascal>Encounter`: `"No <Form Name> encounter recorded yet"`
     - `no<Pascal>Body`: `"No clinical intake details have been submitted for this patient yet."`
     - `no<Pascal>Recorded`: `"No <Form Name> recorded"`
     - `record<Pascal>`: `"Record <Form Name>"`
     - `update<Pascal>`: `"Update <Form Name>"`
   - Inserted directly into `translations/en.json` before the closing brace without re-sorting the whole file.
6. **Obviously Unfinished Stubs**:
   - `hasData: false` in `initialAiims<Pascal>Data`.
   - Prominent `// TODO: Map observations from encounter to concept UUIDs` comments.
7. **Clean Test Template**:
   - Remove unused imports (`vi`, value import of resource).
   - Only test valid components: render card headings, and test dashboard renders empty state when `hasData: false`.
8. **Rollback & Safety**:
   - Wrap process in a transaction. If `tsc` or `vitest` fails on the new form:
     - Remove created directory `src/<key>/`.
     - Revert edits to `form-uuids.ts`, `form-registry.ts`, and `en.json`.
     - Re-run `generate-routes` to restore clean state.
     - Print error message.
     - If `--keep-on-fail` is supplied, retain files for inspection.
- **Acceptance Check**:
  - Scaffold a dummy form: `npm run create-form -- dummy-test-form "AIIMS Visit: Dummy Test Form" --icon=Activity`.
  - Confirm `npm run typescript` and `npm test` pass.
  - Confirm `src/routes.json` contains `dummy-test-form`.
  - Roll back dummy form (or run rollback test).
  - Confirm `git status` is clean.

### Phase 5: Minimal E2E Smoke Test (`npm run test:e2e`)

**Goal:** Catch blank screens or broken Single-SPA component registrations across all registered forms in a real patient chart.

#### Implementation Design
- **Preconditions**:
  - Local Docker stack is running.
  - Test patient exists (e.g. `1d678f66-801a-4a52-b47f-29854389c09f`).
  - Pre-flight check fails early with an actionable message if stack is down or patient is missing.
- **Test Runner**: Playwright (`@playwright/test` running headless Chromium).
- **Test Logic**:
  1. Login via `http://localhost/openmrs/spa/login` with `admin` / `Admin123`.
  2. Navigate to `http://localhost/openmrs/spa/patient/1d678f66-801a-4a52-b47f-29854389c09f/chart`.
  3. Dynamically import `FORM_REGISTRY` from `src/config/form-registry.ts`.
  4. For each entry in `FORM_REGISTRY`:
     - Click the sidebar dashboard link (or navigate directly to `/chart/${entry.path}`).
     - Assert that the container `.omrs-main-content` or dashboard shell mounts.
     - Assert that either the clinical observation cards or the Carbon `EmptyState` (`<h3>` heading) is visible.
     - Assert page is NOT blank (`body` text length > 50 characters, no uncaught error boundaries).
  5. *Do NOT assert on `console.error` initially* (prevents false positives from harmless upstream OpenMRS warnings).
- **Acceptance Check**:
  - Run `npm run test:e2e`.
  - All 26 registered forms pass smoke validation without blank screens.

### Phase 4: Minimal Concept Validator (`scripts/validate_concepts.py`)

**Goal:** Verify that every concept UUID defined in the frontend exists in OpenMRS and has the expected datatype.

#### Implementation Design
- **Core Scope**:
  1. Parse `CONCEPTS` dictionary from `src/config/concepts.ts`.
  2. Query OpenMRS REST API: `GET /ws/rest/v1/concept/{uuid}?v=custom:(uuid,display,datatype:(name))`.
  3. Assert each UUID exists (HTTP 200).
  4. Output summary table: Total concepts, valid concepts, missing/orphaned concepts.
  5. (Form schema cross-checking is deferred until this core check passes).
- **Acceptance Check**:
  - Run `python scripts/validate_concepts.py`.
  - Reports status of all 247+ concepts against the running Docker backend.

### Phase 2: Translation Audit via Existing Tooling (`npm run audit-i18n`)

**Goal:** Leverage the repo's existing `i18next-parser` (`tools/i18next-parser.config.js`) without duplicate custom parsers.

#### Implementation Design
- The repo already has `"extract-translations": "i18next ... --config ./tools/i18next-parser.config.js"`.
- A thin check script (`scripts/audit-i18n.ts`) will:
  1. Run `i18next-parser` to extract code keys to a temp catalog.
  2. Compare the extracted catalog against `translations/en.json`.
  3. Report any keys used in code that have an empty string or are missing from `en.json`.
- **Acceptance Check**:
  - Run `npm run audit-i18n`.
  - Confirms translation completeness with 0 discrepancies reported.
